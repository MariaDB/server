MDEV-37607: WSREP Binlog Transaction Coordinator
================================================

9. IMPLEMENTATION PLAN (PHASES)
===============================

Three phases. Each leaves the server working and is verified with the Galera cluster suites, with
and without the binlog, before the next starts.

Phase 1: the server owns the order
----------------------------------

Goal. One component in the server holds the chain, the release and the abort logic; group commit has
no provider names.
What changes. The tail pointer and the helpers move into Commit_order_manager. A provider adapter
replaces the provider tests. The inline block in binlog group commit becomes one generic release
call with named result fields.
What stays. The Galera library and its commit monitor. Behavior is identical.
Exit. Suites show only the failures of the unmodified base.

Phase 2: tickets and the wait move to the server
------------------------------------------------

Goal. The library reports the order, the server waits.
What changes. The commit order service is added. The library registers a ticket per certified seqno,
in order, for every kind of write set (commits, fragments, dummy write sets, DDL, non-blocking
operations, views). Commits wait in the server and bind the ticket. The manager gets the seqno list,
the tracker, abort, interrupt, the blocker report and stuck escalation.
What stays. The commit monitor still exists for what is not yet ticketed (IST, no binlog).
Exit. Commit order in the binlogs of all nodes is identical under load, with DDL, streaming
replication and replay; no ticket is left over.

Phase 3: the library bypasses its commit monitor
------------------------------------------------

Goal. When the server provides the commit order service, nothing orders commits in the library.
What changes. IST write sets and views get tickets. Tickets are registered without a binlog too and
released at the ordered commit stage. DDL waits for every earlier seqno through the service. The
monitor's other jobs (donor drain, resync, replay wait, pause, state transfer reset) use the apply
monitor. The library selects CommitOrder::BYPASS when the service is provided. The commit monitor,
its statistics and its parameter stay for servers that do not provide the service.
What stays. The commit monitor (not used with the service), the apply monitor and the apply order.
Exit. Suites with the debug and release libraries pass, with and without the service; the
benchmark shows no regression without a binlog.

Estimates
---------

Initial estimate from the MDEV-37607 epic, to be revisited after the design review.
- Implementation: 15 days.
- Testing: 8 days, an estimate. The testing team will give the exact time.
- Total: 23 days.

Testing plan
------------

- Existing suites: all galera suites (galera, galera_sr, galera_3nodes, galera_3nodes_sr) and wsrep,
  with and without the binlog, on debug and release builds. Because binlog group commit changes,
  also binlog, binlog_encryption, binlog_in_engine, rpl and sys_vars, and a build without wsrep.
  Compare the failures with the unmodified base.
- New tests: at least one per requirement; each requirement names its test.
- Failure cases: node failure, a commit that never finishes, brute-force abort and replay, view
  change, IST.
- Compatibility: older and newer server and library combinations.
- Throughput: compare with and without the binlog, with a balanced run order and repeated runs.
