# MDEV-40012 Parallel Query: execute the join in the worker threads

`6c7d3fd5956`. The workers stop shipping raw source records for the manager to
join. Each one now runs the join and the WHERE over its own chunk of the driving
table and ships the base-table columns of the rows that qualified; the manager
copies those columns back into its own table instances, so its records hold what
a serial scan would have left there, and evaluates the select list against them.

This is a port. The work was written on `bb-13.1-pscan-test` in
`~/src/mariadb/13.0-MDEV-39492` and does not apply cleanly here: this tree
regrouped the PWT structures, renamed the handler parallel-scan API, and — the
part that changes behaviour rather than spelling — deep-copies Items further
than the 13.0 branch does, so expressions that branch refuses reach a worker
here.

## Reading order

Four independent reviews, in the order that needs the least prior context:

| Review | Where | The question |
|---|---|---|
| Gate & dispatch | `sql_select.{cc,h}`; section 1 of `sql_parallel_execution.cc` | is the admitted set of queries correct and complete? |
| Worker execution | rest of `sql_parallel_execution.cc`, by section banner | does a worker compute what a serial nested loop would? |
| Threads & channel | `sql_parallel_workers.{cc,h}` | is hand-off, kill and teardown safe? |
| Item layer | `sql/item.{cc,h}`, 13 lines | is un-guarding `item_clone_shares_nodes()` for release builds sound? |

`sql_parallel_execution.cc` is ordered for this: six banner-marked sections in
the order the query travels — gate, entry point, expression cloning, the
worker's copy of the plan, running the join, the manager's drain. Each banner
also names the thread its section runs on, which is the distinction that has to
be held in mind throughout and is not visible from a signature.

A caveat for the threads & channel review: 139 of the 445 deleted lines in
`sql_parallel_workers.cc` reappear verbatim in the new file, so its diff mixes
"moved away" with "actually changed" and the two cannot be told apart by
reading the diff alone. Compare the two files at HEAD instead.

### The two that are not upstream

Both are needed because this tree's `Item_cache::deep_copy()` and
`Item_ref::deep_copy()` clone their children, where 13.0's are shallow. There a
correlated condition shares nodes with the original and the gate refuses it; here
the copy is clean and reaches a worker.

- **`pwt_item_reads_a_foreign_table()`.** `t1.f1 IN (SELECT f1 FROM t4)` run as a
  subquery puts the workers on t4 under `t4.f1 = <outer ref to t1.f1>`. The copy
  is a proper deep copy, so the node check passes it, but `Pwt_field_rebinder`
  has no table to rebind that leaf to and it stays on the manager's t1 — the
  worker then trips `Field::val_int()`'s `in_use` assert. The check also covers
  const tables, which the rebinder's comment called "read-only and safely
  shared"; the same assert says otherwise.
- **`thd->query_id` handover.** `Item_func_curtime`, and NOW/SYSDATE with it,
  recomputes only when `thd->query_id` has moved past its own `last_query_id`.
  A background THD starts at query id 0, which is also that field's initial
  value, so a clone made before the manager had evaluated it looked current to
  the worker and handed out its uninitialized `MYSQL_TIME` —
  `Time::Time()`'s `is_valid_value_slow()`. Reproduced with a single worker, so
  it is staleness, not a race. The 13.0 branch never touches `query_id` in this
  file at any commit and likely carries the same hole latently.

## Verified

In-source debug build (`DBUG_ASSERT`s live), full `make -j16` after each core
file touched. `mtr` green on: `parallel_query`, `parallel_query_join`,
`parallel_query_worker_side`, `parallel_query_clone`, `parallel_query_fallback`,
`parallel_query_oom`, `parallel_query_snapshot`, and on `select`, `join`,
`join_outer`, `subselect`, `subselect_sj`, `subselect_sj2`, `derived_opt`,
`group_min_max`, `status`, `information_schema`, `type_temporal_innodb`,
`func_time`.

The file split was verified by unit inventory (13 units left in
`sql_parallel_workers.cc`, 27 moved, none duplicated or dropped) and by a clean
link. The later reorder into six sections was verified to be a pure permutation:
sorting the non-blank lines of the file before and after gives an identical
multiset apart from the 13 new banner lines. It satisfies every
definition-before-use constraint among the 10 statics and 2 visitor classes
without a forward declaration.

The renames are compiler-checked, and no file outside these three referenced any
of the names. `git show HEAD -- sql/sql_parallel_workers.h` is the shortest way
to see the resulting data model.

## Known gaps

- `a86127a0418` ("check every table the worker will open") is **not** ported. A
  materialized derived table or subquery as an inner table still reaches
  `open_worker_tables()`, whose share was built in memory rather than read from a
  .frm, and `open_table_from_share()` walks off the end of it. On the 13.0 branch
  this was the largest group of crashes when the whole main suite ran with
  `parallel_worker_threads` forced on.
- `103a97fe7e5` ("a worker's result table belongs to the worker") is not ported.
- `d02f7e3c12d` ("workers evaluate with the session's variables") is not ported:
  worker THDs still start from the global `time_zone`, `sql_mode`,
  `default_week_format` and `old_behavior`, so a session that has set any of them
  gets a different answer from a worker than from a serial scan.
- `parallel_query_excluded` does not exist in this tree, so the gate's exclusions
  have no test of their own here.
- `PWT_CHUNK_ROWS` is 128 with `//#define PWT_CHUNK_ROWS 2048` above it, carried
  verbatim from `bbe40d70054`. Looks like the author's debugging leftover.
- `can_run_query_in_workers()` is 156 lines, about 75 of them fifteen
  repetitions of `{ DBUG_PRINT("info", (reason)); DBUG_RETURN(false); }`. It is
  the function that defines the feature's scope and will be re-read every time
  the gate is widened; a `PWT_REFUSE("reason")` macro would collapse each
  condition to one line and turn the body into the checklist its own doc comment
  describes in prose. Deliberately not done here — it would have buried the
  behavioural hunks under a rewrite of the same function.
- `abort_worker()` still stutters as `worker->abort_worker()`. Left alone: the
  obvious `abort()` shadows libc's inside the class, so a future unqualified
  `abort()` call in a member would silently resolve to it.
